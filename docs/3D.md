# 3D

Built with [React Three Fiber](https://r3f.docs.pmnd.rs/), [drei](https://drei.docs.pmnd.rs/) and [@react-three/postprocessing](https://react-postprocessing.docs.pmnd.rs/). Three separate canvases, each client-only behind a `next/dynamic(..., { ssr: false })` wrapper:

| Canvas | Wrapper (safe to import from server code) | When it runs |
| --- | --- | --- |
| Intro vault gate | `gate/IntroGate.tsx` → `gate/GateCanvas.tsx` | Until the visitor unlocks or skips |
| Hero pillars | `canvas/HeroScene.tsx` → `canvas/HeroCanvas.tsx` | While the hero is on screen |
| Rolling balls | `balls/RollingBalls.tsx` → `balls/BallField.tsx` | After the gate, site-wide, only when something moves |

## Sequence

`IntroGate` → (`gateStore.open()`) → pillars rise one by one → hero copy reveals → balls pop onto the pillar crowns → balls roll down the page with the content as the visitor scrolls.

Timings live in `intro` in `src/lib/gate.ts` (`pillarStagger`, `pillarRise`, `text`, `balls`). Anything that should wait for the gate uses `useGateOpen()` (React) or `secondsSinceOpen()` (per frame).

## 1. Intro vault gate (`src/components/gate/`)

- **Model:** `public/models/gate.glb`, generated by `blender/build_gate.py`. See [BLENDER.md](BLENDER.md) for the node-name contract and the realism checklist.
- **Interaction (`IntroGate.tsx`):** drag anywhere. The angle is measured around the wheel's on-screen centre (projected each frame by `GateCanvas` into `GateControl.dial`), so it feels like gripping the rim. Holding → / D / Space / Enter also turns it. The wheel coasts with inertia, never turns back past 0, and ticks every 15°. A coral SVG arc around the wheel shows progress.
- **Unlock timeline (`GateCanvas.tsx`, `T`):** glow → pins retract → cross-bolts slide → doors unseal → doors slide into their pockets → camera pushes into the chamber. The overlay fades at 2.9 s and the gate unmounts at 3.6 s (`FADE_AT`, `OPEN_AT`).
- **Look:** drei `<Environment>` softboxes (reflections), shadowed spot key, N8AO, bloom on the `Glow` material, grain + vignette. Phones (`lowDetail`) drop shadows and AO.
- **Sound (`sound.ts`):** procedural Web Audio, no files. Mute button in the top bar.
- **Config:** `siteConfig.gate`: `enabled`, `model`, `turns`, `oncePerSession`. Reduced motion skips the gate.

## 2. Hero pillars (`src/components/canvas/`)

`HeroCanvas` (`<Canvas>`, post effects, perf monitor, off-screen pause) → `Studio` (lights + environment) and `BeadArches` (the sculpture).

- Each arch is a Catmull-Rom curve (`ARCH_PATH`). Rings of beads are placed along it with Frenet frames; alternate rings are offset half a bead.
- All beads (~3,800) are one `InstancedMesh`, so a single draw call. Instance matrices are written directly for the ripple and the entrance.
- **Entrance:** each arch starts `RISE_FROM` below and rises with an out-quart ease, staggered by `intro.pillarStagger`, once the gate opens.
- Tweak: `ARCHES`, `RING_RADIUS`, `BEAD_RADIUS`, `RIPPLE`, ring/bead counts in `buildInstances(...)`. Material and light colours: `siteConfig.scene`.
- `PerformanceMonitor` drops DPR 1.5 → 1 on slow GPUs; phones get fewer beads; reduced motion disables entrance, breathing and ripple.

## 3. Rolling balls (`src/components/balls/`)

Three beaded balls (pearl, coral, steel — light finishes that read on the dark page). They start on the pillar crowns, then travel down the page **with the content**: every ledge, in order, at the reader's pace.

- **Make an element a ledge:** add `data-ball-floor` to it. Its **top edge** is something a ball rolls along. Mark headings, paragraphs, list items, rows and small cards. An element that contains other ledges is ignored (the balls ride its contents, not its outline). Ledges at the same height that touch are merged into one surface.
- **Route (`physics.ts`):** pure TS, in document pixels. All ledges are sorted top to bottom (`buildRoute`). Ball *j* follows the ledge that last crossed `PHYS.anchors[j]` of the viewport height (`routeTarget`), so the three balls sit at different heights. While the reader scrolls it rolls along the ledge from where it landed toward its exit — the end nearest the next ledge, or the far end on stacked items if the scroll leaves time (`exitEdge`) — then rolls off and drops or hops onto the next ledge (`planFlight`), with a squash and one small bounce on hard landings. It advances one ledge at a time; in multi-column layouts it stays in its column when a ledge sits right below (`nextLedge`), and the other balls pick up the side columns.
- **Pace:** the scroll position, not a timer, decides where a ball should be, so balls stop when the reader stops. A ball that falls behind rolls faster and hops quicker (`catchUp`, flight `boost`); only ledges already sliding under the navbar are skipped. A ledge about to go under the navbar hands the ball to the next one as soon as that is on screen; with a long gap the ball waits on the bottom edge of the screen until the next ledge comes up and carries it.
- **Behaviour (`BallField.tsx`, `Mode`):** scrolling up `LEAVE_AFTER` px makes the balls hop off the nearer side of the screen; scrolling down `RETURN_AFTER` px (or reaching the top) drops them back in from above onto the ledge the scroll position says. Clicking/tapping a ball charges it (swells, beads spread, coral core and inner light glow) for `CHARGE` s, then it dashes to a random ledge on screen in `DASH` s and stays there until the reader scrolls `UNPIN_AFTER` px. The canvas ignores the pointer, so balls are hit-tested from a window `pointerdown` listener.
- **Ledges near the screen edge** are inset by 2.2 × the ball radius so balls can always roll off full-width cards (phones).
- **Rendering (`BallField.tsx`):** a fixed transparent canvas (`z-40`, below the navbar) with an orthographic camera where 1 unit = 1 CSS px. `frameloop="demand"`: it only renders when a ball moves or the page scrolls.
- **Pillar crowns:** `PILLAR_CROWNS` are measured fractions of the hero canvas. Re-measure if you change `ARCHES`, the hero camera, or the hero canvas height. Crowns off screen (the side ones on phones) are left out of that ball's route.
- **Config:** `siteConfig.balls`: `enabled`, `count`, `radius.desktop/mobile`, `materials` (one finish per ball: `color`, `core` = the shadowed inside seen between beads, roughness/metalness/clearcoat/envMapIntensity). Off for reduced motion.
- **Tune feel:** `PHYS` in `physics.ts` (`anchors`, `rollSpeed`, `catchUp`, `gravity`, `minHop`, `bounceSpeed`, `squashKick`…).

## Swapping in a model

1. Export `.glb` (Blender: File → Export → glTF Binary, or a script like `blender/build_gate.py`; Unity: *UnityGLTF*). Optimise: `npx gltf-transform optimize in.glb out.glb --compress draco`.
2. Put it in `public/models/`.
3. `npx gltfjsx public/models/scene.glb -t -o src/components/canvas/Model.tsx`
4. Render `<Model />` inside the relevant canvas (wrap in `<Suspense>`), and `useGLTF.preload(...)`.

## Performance checklist

- Measured in Chrome on an Intel UHD (integrated) at 1440×900: gate 120+ fps with all effects after warm-up; hero ~46 fps on an older Iris Plus 645. The first second after load is slow while shaders compile and the GLB decodes, so don't drive game logic off a fixed per-frame step.
- Avoid `setState` in `useFrame`; mutate refs. Name refs passed as props `somethingRef` (React Compiler lint treats them as mutable).
- Keep post effects light. Gate: AO + bloom + grain + vignette. Hero: grain + vignette.
- Turn things off: `siteConfig.scene.enabled`, `siteConfig.gate.enabled`, `siteConfig.balls.enabled`.
- Visual check without a human: `playwright-core` driving installed Chrome with `--use-angle=d3d11` gets the real GPU (see the `add-3d-scene` skill).
